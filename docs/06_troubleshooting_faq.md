# 疑难排障与常见问题 FAQ

整理了在部署与使用本项目过程中可能遇到的典型问题及其深度排查方法。

---

### Q1: 为什么回看播放 38 秒就卡死，或者每 16 秒卡顿一次？
- **现象**: 播放器开始很流畅，但播放 16 秒或 38 秒后画面定格，进度条停止。
- **根本原因**: 电信 FonsView CDN 对单个长连接实施了流量整形（QoS），单个 TCP 连接传输满 23MB 后，带宽会被骤降至 240 KB/s（1.9 Mbps），而高清流需要 9.2 Mbps，导致播放器缓冲耗尽。
- **解决方案**: 本项目新版已内置切片流水线预读引擎，确保每个切片以独立的短连接并携带 `Range: bytes=0-` 拉取，避开限速区间，并在本地 SSD 保持 2 个切片的超前缓冲。请确保已升级至最新编译版本。

---

### Q2: 为什么测试时下载 300KB 数据后就彻底停滞断流？
- **现象**: curl 或播放器刚连上几百毫秒就断流，抓包显示服务端不再发送后续包。
- **根本原因**: **物理机顶盒依然开机并联网！**
  虚拟机克隆了物理机顶盒的 MAC 和 IP。由于机顶盒会周期性发送 mDNS/SSDP 广播，光猫内部交换机产生 **MAC 地址漂移**，将后续所有的视频流转发给了物理机顶盒，虚拟机端直接丢包超时。
- **解决方案**: **彻底拔掉物理机顶盒的网线或关闭机顶盒电源**。局域网内只能保留虚拟机一台设备使用该 MAC 地址。

---

### Q3: 为什么刚播完的节目点回看提示 `051003 未获取到节目播放地址`？
- **现象**: 在 EPG 点击刚刚结束（如结束仅 3~5 分钟）的节目回看时失败。
- **根本原因**: 电信机房录制系统在节目直播结束后，需要 **15 ~ 30 分钟** 的切片索引与分发处理期。在此期间，点播服务器尚未收录该节目的完整 HLS 播放列表。
- **解决方案**: 这是电信服务端的数据生成延迟。请稍等约 15~30 分钟后再点播该节目；或者点播该节目播出前半段、昨天/前天的节目，即可秒开。

---

### Q4: 电视机只有 100 Mbps 百兆网卡，会成为回看瓶颈吗？
- **完全不会**。
- CCTV-5 等 1080P 高清频道码率为 **9.2 Mbps**。百兆网卡（100 Mbps）具有 **10 倍以上** 的余量空间。
- 在百兆有线下，电视机从部署在内网的虚拟机拉取一个已缓存的 10 秒分片（11MB）仅需 **0.9 秒**，播放速度是下载速度的 1/10，绝不会发生缓冲饥饿。

---

### Q5: 组播直播（Live）无法播放或黑屏？
- **排查步骤**:
  1. 检查 `udpxy` 服务是否正常运行：
     ```bash
     ps aux | grep udpxy
     ```
  2. 检查组播路由是否已添加至 `eth0.85` 网卡：
     ```bash
     ip route show | grep 239
     # 必须存在：239.0.0.0/8 via 30.120.0.1 dev eth0.85
     # 必须存在：233.18.204.0/24 via 30.120.0.1 dev eth0.85
     ```
  3. 测试 udpxy 直通取流：
     ```bash
     curl -i "http://172.16.0.5:5140/rtp/233.18.204.188:5140" | head -c 1000
     ```
     如果能收到以 `0x47`（ASCII 'G'）开头的二进制数据，说明组播完全正常。

### Q6: 多台设备同时观看回看，磁盘空间会爆满吗？
- **不会**。
- 缓存引擎内部实现了严格的 **LRU 淘汰机制**，默认上限 `MaxCacheFiles = 30`（总容量约 300MB）。
- 当分片超过 30 个时，系统会自动清理最久未被访问的切片，始终将磁盘占用控制在 300MB 以内，在任何低配虚拟机/软路由上都能常年无人值守稳定运行。
